# Boardwright README Rewrite Draft

This file is the working brief for replacing the inherited root `README.md`
with a Boardwright-native README. The root README is also generated by KiBot in
project workflows, so this draft separates repository documentation decisions
from generated project README behavior.

## Positioning

Boardwright is a KiCad/KiBot hardware project template with a workflow cockpit.
It is for PCB projects that want repeatable previews, reviewed accepted outputs,
and release packages without making designers operate git and CI by memory.

The plain-language loop:

```text
edit in KiCad -> record changes -> commit + push -> review artifacts
-> accept to main -> create release
```

The product should feel boring in the best way: clear state, clear next action,
and no surprise branch or tag mutations.

## What The Repository Contains

- KiCad template project files at the repository root.
- KiCad worksheet/title-block templates in `Templates/`.
- Boardwright project configuration in `.boardwright/`.
- GitHub Actions workflows in `.github/workflows/`.
- Boardwright CLI/TUI package in `src/boardwright/`.
- Boardwright/KiBot support resources in `boardwright_resources/`.
- Source assets in `assets/`.
- Planning and implementation docs in `docs/`.
- Regression tests in `tests/`.

Generated KiBot outputs such as `Manufacturing/`, `Schematic/`, `Reports/`,
`HTML/`, `KiRI/`, and `Testing/` are not part of the clean source tree.

## User Quick Start

From the repository root:

```powershell
.\scripts\install_boardwright.ps1
boardwright
```

For a project-local install:

```powershell
.\scripts\install_boardwright.ps1 -Scope Project
.\boardwright.ps1
```

The project-local path keeps each hardware project pinned to its local
Boardwright checkout. The global command can also be configured to prefer the
nearest project-local install before falling back to the user/global install.

## Normal Workflow

1. Create or open a Boardwright-based KiCad project.
2. Work on schematic, PCB, documentation, or project files on `dev`.
3. Run `boardwright`.
4. Record what changed.
5. Commit and push to `dev`.
6. Review preview artifacts from CI.
7. Accept a reviewed state to `main`.
8. Check release readiness and create a draft, prerelease, or release tag when
   appropriate.

## TUI Actions

Primary actions:

- Record Changes
- Commit + Push
- Review Artifacts
- Accept to Main
- Create Release
- Refresh

Things the user should not normally have to run by hand:

- validation
- revision-history variable generation
- raw workflow dispatch
- raw git status
- legal/notice generation

Those stay automatic, CLI-only, or advanced fallback paths.

`Create Release` should always show a final readiness checklist before it
dispatches CI-owned release preparation. That checklist confirms accepted-main
output freshness, release inputs, changelog readiness, local tag availability,
and the dispatch target.

## Branch And Release Model

- `dev` is the normal working branch.
- Preview CI runs from `dev` and is disposable.
- `preview` is a disposable generated branch.
- `main` is the accepted project state.
- `main` should only receive source files plus accepted README/render snapshot
  assets needed for the front page.
- Tags are immutable release package points.
- Tag workflows publish release artifacts without mutating branches.
- Drafts, prereleases, and releases are explicit user decisions.

## Generated Outputs

Preview and release generation is CI-first for now. Local KiBot/Docker running
can be added later, after the GitHub Actions workflow is reliable.

Visible generated media is organized under:

```text
assets/logos/
assets/renders/
assets/3d/
```

`assets/renders/` may be committed to `main` as an accepted README snapshot.
Full manufacturing/release outputs are workflow artifacts and release assets,
not routine source-branch commits.

## Development Notes

Run validation through the CLI module:

```powershell
python -m boardwright validate
python -m boardwright.cli validate
```

Check local workflow readiness before live CI testing:

```powershell
python -m boardwright doctor
```

Plan an isolated live-test repository:

```powershell
python -m boardwright testbench plan --github-repo OWNER/boardwright-live-test
```

See `docs/TESTBENCH.md` for the full separate-repo test flow.

Run tests with:

```powershell
python -m unittest discover -s tests -v
```

The installed console command is still the normal user-facing entry point:

```powershell
boardwright
```

## Licensing And Attribution

Boardwright is derived from Nguyen Vincent's KiCad/KiBot template work,
originally published as `KDT_Hierarchical_KiBot`.

The current repository still contains inherited material, including KiCad
worksheet/title-block templates, KiBot configuration patterns, support scripts,
fonts, colors, workflow structure, and parts of the original documentation.

The inherited template is MIT licensed. The preserved license text remains in
`LICENSE`. Current inherited-material notes live in
